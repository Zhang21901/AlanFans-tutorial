# 不用服务器，15 分钟监控 X 动态并自动推送到飞书

**用 GitHub Actions + RSSHub + Python 做一个不需要常驻电脑的消息机器人**

我最近做了一个很小但很实用的自动化工具：持续监控一个 X 账号，只要对方发了新帖子，就自动把正文和原文链接推送到飞书群。

它不需要买服务器，不需要自己的电脑一直开机，也不会把历史帖子一次性刷屏。整个系统由 GitHub Actions 定时唤醒，每 15 分钟检查一次；没有新动态时安静结束，有新动态时才通知。

完整的脱敏模板和教程在这里：

https://github.com/Zhang21901/AlanFans-tutorial

## 为什么要做这个

很多信息源只在 X 发布，而团队协作、知识沉淀和日常沟通却发生在飞书。手动盯着动态既容易遗漏，也会频繁打断工作。

我希望实现的是：

- 不用打开 X，也能在飞书群第一时间看到新动态。
- 不需要维护 VPS、云函数或本地常驻脚本。
- 不重复推送同一条内容。
- 首次部署时不推送旧帖子，避免群聊被历史消息刷屏。

## 整体架构

一次检查的流程如下：

```text
GitHub Actions 定时触发
        |
        v
临时启动 RSSHub 容器
        |
        v
把 X 动态转换为 RSS
        |
        v
Python 读取 RSS 并与 state.json 比较
        |
        +--> 无新帖子：结束
        |
        +--> 有新帖子：发送飞书卡片并更新 state.json
```

这里有两个关键设计。

第一，GitHub Actions 不是一台一直运行的服务器。每 15 分钟，GitHub 会临时分配一台 Runner 执行几十秒；任务结束后，Runner 和 RSSHub 容器都会自动销毁。

第二，`state.json` 会被任务自动提交回 GitHub 仓库。这个文件只记录已经处理过的帖子 ID，所以即使下一次是在全新的 Runner 上执行，程序也能知道哪些消息已经发过。

## 我用了哪些组件

- **GitHub Actions**：负责定时调度、运行 Python、保存状态。
- **RSSHub**：把 X 用户动态转换成 RSS，方便程序读取。
- **Python + requests + feedparser**：解析 RSS、判断增量、调用飞书 Webhook。
- **飞书自定义机器人**：接收交互式卡片消息。

为了避免依赖不稳定的公共 RSSHub 实例，工作流会在 GitHub Runner 内临时启动 RSSHub Docker 容器，再从 `127.0.0.1` 读取 RSS。这样不需要自己购买或维护服务器。

## 配置只需要三个 Secret

所有敏感信息都配置在 GitHub 仓库的：

```text
Settings -> Secrets and variables -> Actions -> Secrets
```

需要创建三个 Repository Secret：

| Secret 名称 | 用途 |
| --- | --- |
| `FEISHU_WEBHOOK` | 飞书自定义机器人 Webhook 地址 |
| `FEISHU_SIGNING_SECRET` | 飞书机器人签名校验密钥 |
| `TWITTER_AUTH_TOKEN` | RSSHub 读取 X 动态需要的认证凭据 |

代码和 Git 历史中不保存这些值。工作流只通过 `${{ secrets.NAME }}` 在运行时读取它们。

飞书消息使用交互式卡片：帖子正文在卡片中展示，底部有“查看原文”按钮。若机器人开启了签名校验，程序会生成时间戳和 HMAC-SHA256 签名后再发消息。

## 如何避免重复推送

首次运行 `monitor` 时，程序会读取当前 RSS 中的全部帖子，只把它们的 ID 写入 `state.json`，不会发到飞书。

之后每次执行时：

1. 拉取最新 RSS。
2. 找出不在 `seen_ids` 中的帖子。
3. 按时间从旧到新发送飞书卡片。
4. 每成功处理一条，就立刻写入 `state.json`。
5. GitHub Actions 自动提交状态文件。

“每条成功后立刻保存”很重要。假设同一轮发现三条新帖子，第二条发送失败，第一条已经保存；下一轮只会重试尚未完成的内容，不会重复打扰群聊。

默认只推送原创帖子，转推会被过滤。需要包含转推时，把工作流里的：

```yaml
FILTER_RETWEETS: "true"
```

改成：

```yaml
FILTER_RETWEETS: "false"
```

## 建议的验证顺序

部署后不要马上等待定时器。GitHub Actions 提供了三种手动模式，建议按顺序验证：

1. `test-message`：只向飞书发送测试卡片，验证 Webhook 和签名。
2. `check-rss`：只验证 RSSHub 是否能读取目标账号，不发送飞书，也不写状态。
3. `monitor`：正式初始化，记录当前历史帖子，但不推送它们。

完成这三步后，工作流会按下面的 cron 规则自动运行：

```yaml
schedule:
  - cron: "*/15 * * * *"
```

这不意味着有一个程序一直在后台运行。每到 15 分钟周期，GitHub 才会创建一次新的短任务。GitHub 的定时任务偶尔延迟几分钟是正常的。

## 这个方案适合谁

它适合：

- 想跟踪少量 X 账号，但不想一直刷新页面的人。
- 需要把公开信息同步进飞书群的个人或小团队。
- 想学习 GitHub Actions、Webhooks、RSS 和状态持久化的人。

它不适合把 X 当成高频爬虫目标，也不适合要求秒级通知或企业级稳定性的场景。

## 关于 X 账号风险

这一点需要明确说明。

当前模板使用 `TWITTER_AUTH_TOKEN` 让 RSSHub 读取 X 动态。它属于登录会话凭据，存在失效、额外验证、访问限制，甚至账号处罚的风险。15 分钟一次的低频检查只能减少请求量，不能消除风险。

因此我建议：

- 不要把 Cookie 写进代码、截图或公开仓库。
- 不要提高轮询频率，也不要同时运行多个同类任务。
- 一旦出现 X 异常登录、验证或限制提示，立即删除 GitHub Secret 并停止工作流。
- 需要长期、稳定、合规地使用时，迁移到 X 官方 API。GitHub Actions 仍然可以承担定时任务，不需要另买服务器。

## 最后

这个项目最有意思的地方不在于“监控 X”，而在于它展示了一种轻量的自动化模式：

```text
定时任务 + 临时计算资源 + Webhook + Git 持久化状态
```

很多个人自动化需求都可以套用这个结构，例如监控博客更新、商品库存、招聘页面、开源项目发布和网站公告。
